# Stateful Ceremony Matrix Example: Local Release and Stub Publication

This is a **planning example**, not authorization, not a product workflow, and not permission to perform real release or publication actions. It exists so a planner can model durable transitions, failure boundaries, rerun behavior, and recovery options **without** touching a real remote, credential, or outward system.

## Safety boundary

Use only a disposable fixture such as:

- disposable repository root: `/tmp/compound-loop-fixture/example-repo`
- local bare remote: `file:///tmp/compound-loop-fixture/example-remote.git`
- stub publication endpoint: `http://127.0.0.1:8787/stub-release`
- credentials: none configured, none required, none retained

Boundary sentinel proof before any example run:

1. every configured git remote resolves to a `file:///tmp/compound-loop-fixture/...` path;
2. every publication endpoint resolves to `127.0.0.1` and the stub fixture identity matches the retained fixture record;
3. the retained evidence records the fixture root, `git remote -v`, stub identity, and an assertion such as `BOUNDARY_SENTINEL=local-only` proving no real target is reachable.

Safe local-only command shapes the example may reference:

- `git -C /tmp/compound-loop-fixture/example-repo status --short`
- `git -C /tmp/compound-loop-fixture/example-repo remote -v`
- `git -C /tmp/compound-loop-fixture/example-repo push file:///tmp/compound-loop-fixture/example-remote.git HEAD:refs/heads/release-test`
- `curl --fail --silent http://127.0.0.1:8787/stub-release/status`

Do **not** substitute a real branch, hosted remote, token, or live publication API.

## Required retained evidence fields for forced failures

Every forced-failure cell below names an injection boundary and the evidence fields needed to prove the intended mechanism failed rather than setup drift or an unrelated validator failure. Retain, at minimum:

- transition ID and outcome class;
- fixture root, configured remotes, stub endpoint, and boundary sentinel;
- exact injection hook or stub mode;
- pre-state fingerprint;
- exit status and concise sanitized output;
- post-state inspection;
- mechanism check tying the observed failure to the intended boundary.

## Outcome matrix

| Transition | Success | Forced failure with expected post-state | Rerun / idempotency | Rollback or compensation | Headless | Cancellation or abort |
|---|---|---|---|---|---|---|
| **T1 — Release commit creation** | A disposable release commit is created in the fixture repo; `HEAD` advances, the working tree is clean, and no tag, remote ref, or publication exists yet. | **Injection boundary:** commit-creation hook blocks immediately before `git commit` finalizes, for example a fixture pre-commit script that exits nonzero only when `FAIL_AT=release-commit`. **Expected post-state:** version files may be edited in the worktree, but no new commit object exists and `HEAD` remains on the prior commit. **Evidence fields:** `git rev-parse HEAD` before/after, staged diff fingerprint, hook marker, exit status, and output proving the hook fired instead of a generic git config failure. | Safe to rerun after clearing the injected hook because no outward state exists yet; either the first successful rerun creates exactly one release commit or a pre-existing identical release commit is detected and reused with an explicit no-duplicate note. | Fully reversible local state: reset or restore the disposable worktree, unstage files, or recreate the fixture repo. No compensation is needed because nothing escaped the fixture boundary. | `mode:headless` is prepare-only in the live release skill: it writes `.release/draft.md` and stops before the USER gate. **Expected post-state:** no release commit is created, `HEAD` stays unchanged, and the retained handoff evidence is the draft path plus the resolved version, source inventory mapping, and Drop-list captured in `.release/draft.md`. | If aborted after files are prepared but before commit finalizes, keep the dirty worktree as the durable local post-state and require the next invocation to either clean it or finish the commit deliberately. |
| **T2 — Pre-tag verification after the commit exists** | Verification runs against the new release commit and passes; commit remains in place, no tag exists yet, and the evidence records the verified commit hash. | **Injection boundary:** verification step fails after the release commit already exists, for example `bash scripts/validate.sh` in the fixture exits nonzero only when `FAIL_AT=pre-tag-verify`. **Expected post-state:** the release commit still exists locally, no annotated tag exists, and no remote or publication state changed. **Evidence fields:** release commit hash, validator mode flag, nonzero exit status, concise failing check output, proof the tag is absent, and a mechanism check showing the injected validator path fired rather than an unrelated missing dependency. | Rerun should be idempotent with respect to the commit: the next pass reuses the same release commit and reruns verification instead of creating a second release commit. If inputs changed, the planner must record whether a replacement commit is allowed before rerun. | Reversible local recovery: either fix the verification issue and rerun on the same commit, or abandon the local commit in the disposable repo by resetting the fixture branch. Because the commit is still local-only, rollback is allowed. | `mode:headless` never reaches Execute or pre-tag verification. **Expected post-state:** the local branch and commit state stay unchanged, no tag exists, and the retained handoff evidence is `.release/draft.md` proving the ceremony stopped before the USER gate with the planned release packet still unexecuted. | If aborted mid-verification, the post-state is still "release commit exists, tag absent, verification incomplete." The next invocation resumes from verification, not from commit creation. |
| **T3 — Annotated tag creation plus tag-only verification** | An annotated tag is created on the verified release commit in the fixture repo, then tag-only verification passes. Post-state: commit and annotated tag both exist locally, with no remote publication yet. | **Injection boundary:** fail immediately after annotated tag creation but during tag-only verification, for example a fixture validator exits nonzero only when `FAIL_AT=tag-verify`. **Expected post-state:** the local annotated tag exists and points at the release commit, but tag-only verification is marked failed and no remote ref changed. **Evidence fields:** tag object id, target commit hash, validator mode flag, nonzero exit status, `git show-ref --tags` output, and mechanism evidence proving the failure happened in tag-only verification rather than tag creation or missing git identity. | Rerun must detect the existing local annotated tag. Idempotent behavior is to reuse the same tag for repeated verification when the tag matches the expected commit; creating a second tag name or silently retagging a different commit is not allowed. | Reversible local state: because the tag is still local-only, the disposable fixture may delete and recreate the tag, or discard the entire repo and rebuild the fixture. Record which recovery path was chosen. | `mode:headless` stops before the USER gate and therefore never creates a tag or runs tag-only verification. **Expected post-state:** commit/tag state is unchanged from pre-headless invocation, and the retained handoff evidence is `.release/draft.md` plus the draft highlights needed for a later first-hand approved run. | If aborted after tag creation but before tag-only verification completes, the durable post-state is "local commit and local tag exist; tag verification incomplete." The next invocation resumes at tag verification or performs an explicit local repair first. |
| **T4 — Commit and tag publication, including partial push** | The disposable release branch and annotated tag are pushed only to the local bare remote. Success means the remote now contains both the intended commit ref and tag, and local evidence shows the remote URL remained inside the fixture boundary. | **Injection boundary:** partial push boundary inside the local bare remote, for example the fixture allows the branch ref update but rejects the tag update when `FAIL_AT=push-tag`. **Expected post-state:** the bare remote contains the release branch commit but does not contain the tag, creating a partial publication state that later invocations must repair. **Evidence fields:** local `git remote -v`, branch ref present on the bare remote, tag ref absent on the bare remote, push exit status, rejected-ref stderr excerpt, and a mechanism check proving the stub rejection created the mismatch rather than a typo in the remote URL or a network failure. | Rerun is a repair step, not a clean slate: it must detect the already-published branch ref and push only the missing tag or otherwise reconcile the partial remote state without rewriting published history. Repeating the exact same push after the branch already exists should leave the remote commit unchanged. | Once the branch ref is visible in the bare remote, treat it as outward state even though the fixture remote is local. Do **not** model rollback as history erasure. Compensation is "repair the missing tag" or "publish an explicit superseding ref/release note in the fixture model"; manual recovery may be required if the published commit was wrong. | Not applicable: the current release skill is local-only, and `mode:headless` never crosses the USER gate into Execute, so it cannot push a branch or tag even to a disposable remote. | If aborted after the branch push succeeds but before the tag push or remote verification finishes, the post-state is a partial publication. The next invocation must inspect remote refs first, then repair or continue; it must not assume nothing was published. |
| **T5 — Release-page publication plus post-publication verification** | The stub release endpoint records one release-page entry referencing the already-published commit and tag, and post-publication verification confirms the stub payload, release identifier, and visibility state. | **Injection boundary:** stub publication accepts creation but post-publication verification fails, or the stub rejects verification mode only when `FAIL_AT=release-page-verify`. **Expected post-state:** the stub may already contain a release-page record even though verification failed; commit, tag, and release-page state are therefore externally visible within the fixture model. **Evidence fields:** stub fixture identity, request id or release id, stored stub payload fingerprint, verification response, exit status, and a mechanism check proving the failure came from the intended stub verification boundary rather than a missing local server or malformed fixture URL. | Rerun must detect whether the stub release-page record already exists. Idempotent behavior is to verify the same record or apply a safe update path defined by the plan; it must not create duplicate release pages silently. | Irreversible outward state: do **not** claim rollback can erase a published release page. Compensation or repair is required, such as marking the stub release entry superseded, publishing a corrected follow-up entry, or recording a manual recovery procedure. | Not applicable: the current release skill is local-only, and `mode:headless` writes `.release/draft.md` then stops before the USER gate, so it never reaches any release-page publication or post-publication verification step. | If aborted after the stub accepts publication but before verification completes, the durable post-state is "release page may already be visible." The next invocation must inspect the stub first and then repair, verify, or supersede; it must not pretend the publication never happened. |

## Self-review checklist for S4

- Covers all five required transitions: release commit, pre-tag verification, annotated tag plus tag-only verification, commit/tag publication with partial push, and release-page publication with post-publication verification.
- Fills all six outcome classes in every row; no blank cells remain.
- Distinguishes reversible local-only states from outward states that require repair, compensation, or manual recovery.
- Names a concrete injection boundary and mechanism-check evidence for every forced failure.
- Proves safe isolation with a disposable repo, local bare remote, stub endpoint, no credentials, and a boundary sentinel.
- Does not change `skills/release/SKILL.md` and does not authorize real push or publication.
